Key Dependencies

Cargo.toml — lean and focused
Crate Purpose Why this one
axum HTTP server Lightweight, async, Tower ecosystem. ~2MB binary contribution.
tokio Async runtime Required by axum. Use rt-multi-thread feature for pipeline parallelism.
ffmpeg-next H.264 decode/encode Safe Rust bindings to FFmpeg's libav*. Battle-tested codecs.
image Pixel buffer ops Load canvas texture, pixel format conversions. Pure Rust.
reqwest HTTP client Fetch .ts segments from EarthCam. Async, TLS built-in.
chrono + chrono-tz London time Time-of-day color palette calculation.
tracing Logging Structured async-aware logging. Replaces Python print statements.
Not included: No OpenCV, no numpy, no pybind11, no Python runtime. The effects pipeline is pure Rust operating on raw pixel slices.

Module Responsibilities

server.rs — HTTP & Lifecycle
  • GET /api/stream → M3U8 playlist
  • GET /api/segments/{id}.ts → segment bytes
  • GET /health → for Fly.io health checks
  • Tracks last client request timestamp
  • Signals pipeline to start/stop based on client activity
pipeline.rs — Orchestrator
  • Owns the main processing loop
  • Coordinates: fetch → decode → effects → encode
  • Manages segment ring buffer (last 10)
  • Spawns blocking work on spawn_blocking
  • Watches for shutdown signal (idle timeout)
effects.rs — Pure Pixel Math
  • apply_distortion() — sine-wave remap
  • quantize() — color posterization
  • detect_edges() — Sobel + threshold
  • blend_texture() — canvas overlay
  • All operate on &mut [u8] slices in-place
codec.rs — FFmpeg Wrapper
  • decode_segment(bytes) → Vec<Frame>
  • encode_segment(frames) → Vec<u8>
  • Handles pixel format conversion (YUV↔RGB)
  • Configures H.264 encoder (CRF, preset)
  • Wraps output in MPEG-TS container

Deployment: Fly.io

Dockerfile — multi-stage build
# Stage 1: Build
FROM rust:1.83-bookworm AS builder
RUN apt-get install -y libavcodec-dev ...
COPY . .
RUN cargo build --release

# Stage 2: Runtime
FROM debian:bookworm-slim
RUN apt-get install -y libavcodec60 ...
COPY --from=builder /app/target/release/morphing .

# Final image: ~80-120MB total
# (vs ~1-2GB for Python + OpenCV + FFmpeg)
fly.toml — auto-stop config
app = "livestream-morphing"
primary_region = "lhr"  # London!

[build]
  dockerfile = "Dockerfile"

[http_service]
  internal_port = 8080
  auto_stop_machines = "stop"
  auto_start_machines = true
  min_machines_running = 0

[[vm]]
  size = "shared-cpu-1x"
  memory = "256mb"

# Cost: $0 when idle
# ~$0.50-2/mo when actively streaming

Why London (LHR) region?

The Abbey Road EarthCam server is in the US, but your viewers likely care about latency to them, not to the source. LHR also makes the London timezone calculation trivial. If latency to EarthCam matters more, switch to ewr (Newark) or iad (Virginia).

Resource Budget

Expected resource usage on shared-cpu-1x (256MB)
Binary size ~10-15MB (release, stripped)
Container image ~80-120MB (with FFmpeg runtime libs)
RAM (idle/sleeping) 0MB (machine stopped)
RAM (streaming) ~60-100MB (pipeline buffers + 10-segment ring buffer)
CPU (per segment) ~2-3s burst on shared vCPU, then idle until next segment
Cold start ~1-2s (Fly machine wake + binary start)
Monthly cost estimate $0-3/mo (free tier covers light usage)
