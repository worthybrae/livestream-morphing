In-Memory Processing Pipeline

Everything stays in RAM — no temp files, no JPEG round-trips

Current Python Pipeline (wasteful)
Download .ts to disk → PyAV reads from disk → Copy to numpy array → Copy to C++ Mat → C++ processes → Copy back to numpy → Write JPEG to disk ×30 → FFmpeg reads JPEGs from disk → Write .ts to disk

⚠ 5+ memory copies per frame, 60+ disk operations per segment, JPEG quality loss

Proposed Rust Pipeline (zero-copy where possible)
HTTP GET → bytes in memory → ffmpeg-next decodes → raw pixels → Rust effects (in-place mutation) → ffmpeg-next encodes → .ts bytes → Ring buffer (serve to clients)

✓ 0-1 copies per frame, zero disk I/O, no quality loss, ~5× less memory

Per-Segment Flow Detail

One 6-second segment lifecycle
Step 1 Fetch — HTTP GET latest .ts segment (~3-5MB) → kept as Vec<u8> in memory ~200ms
Step 2 Decode — ffmpeg-next reads from memory buffer, yields ~180 raw pixel frames ~300ms
Step 3 Process — Each frame: quantize + edge detect + texture blend (in-place on pixel buffer) ~30-80ms/frame
Step 4 Encode — ffmpeg-next encodes processed frames → H.264 MPEG-TS bytes ~500ms
Step 5 Buffer — Store encoded .ts bytes in ring buffer (last 10 segments). Generate M3U8 playlist from buffer. ~0ms
Total: ~2-4 seconds per segment (vs current ~6-10s) on a single vCPU.
RAM usage: ~30-50MB for pipeline + ~30MB for 10-segment ring buffer = ~60-80MB total

On-Demand Lifecycle

How the service wakes and sleeps
SLEEPING Container exists but has 0 CPU allocation (Fly.io machines / Railway sleep)
↓ Frontend sends GET /api/stream
WAKING Container cold-starts (~1-2s for Rust binary), returns empty M3U8 playlist
↓ Pipeline starts fetching Abbey Road stream
BUFFERING First 3 segments processed (~10-15s). Frontend shows loading state.
↓ 3+ segments ready
STREAMING Continuous processing. M3U8 playlist updates. Clients play video.
↓ No client requests for 5 minutes
SLEEPING Pipeline stops, buffer cleared, container goes to sleep. $0 cost while idle.
