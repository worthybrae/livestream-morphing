Three Approaches for the Rust Rewrite

Each takes a different stance on how much to replace and how lean to go

A

Full Rust Binary — "The Monolith"

Replace everything: fetching, H.264 decoding, image processing, H.264 encoding, HLS serving — all in one Rust binary.

Pros

  • Smallest possible footprint (~10-30MB binary, ~50-100MB RAM)
  • Zero external dependencies — no FFmpeg, no Python, no system libs
  • Fastest cold start (~1-2s for just the binary)
  • Single container, trivial deployment
  • Zero-copy frame pipeline (decode → process → encode in shared memory)

Cons

  • Hardest to build — H.264 decode/encode in pure Rust is complex
  • Rust video codec ecosystem is less mature (openh264, rav1e)
  • Longest development time

Target: ~50-100MB RAM, 0.5 vCPU sustained, $0-5/mo on Fly.io

B

Rust Core + FFmpeg Libs — "The Hybrid"

Rust does orchestration + image processing. Links against FFmpeg's libavcodec/libavformat for decode/encode (via the ffmpeg-next crate). No Python at all.

Pros

  • Battle-tested H.264 codec (FFmpeg is the gold standard)
  • Still very lean (~100-200MB RAM with FFmpeg linked)
  • Much faster to build — focus effort on the effects pipeline
  • Zero-copy between decode → Rust processing → encode
  • Single process, no subprocess spawning

Cons

  • Needs FFmpeg libs in the container (adds ~30-50MB)
  • FFmpeg C bindings can be fiddly to cross-compile
  • Slightly larger container than pure Rust

Target: ~100-200MB RAM, 0.5-1 vCPU sustained, $0-5/mo on Fly.io

C

Rust Processing + Existing Python Shell — "The Transplant"

Replace only the hot path: Write a Rust library for image effects, call it from Python via PyO3 (like the current C++/pybind11 setup). Keep FastAPI, PyAV, FFmpeg subprocess.

Pros

  • Fastest to build — smallest change surface
  • Rust effects may be faster than C++ (SIMD, better optimizer)
  • Low risk — can A/B test against current C++ processor

Cons

  • Doesn't solve the core problem — still need Python + FFmpeg + all deps
  • Still ~500MB+ container, still high memory usage
  • Won't run on free tier — same resource hunger
  • Doesn't enable on-demand cold start pattern

Target: Same as current, marginal frame processing improvement only

My Recommendation: Option B

Option A is the dream but the Rust pure-video codec ecosystem isn't mature enough to justify the risk. Option C doesn't solve your actual problem. Option B gives you 90% of the benefits — a single lean Rust binary that links FFmpeg for the codec work it's best at, while Rust handles everything else (HTTP, HLS, image processing, scheduling). Should comfortably run on a Fly.io free-tier machine.
