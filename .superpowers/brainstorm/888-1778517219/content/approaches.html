Studio Architecture — 3 Approaches

How should the studio UI be built and served?

A

Single HTML + WebSocket (Recommended)

One self-contained HTML file served from the existing Axum server. Vanilla JS, no build tools. WebSocket pushes real-time parameter changes to the effect pipeline.

Pros

  • Zero frontend build tooling — just HTML/CSS/JS
  • Single binary deployment, same as today
  • WebSocket gives instant feedback (no polling)
  • Easy to hack on — edit one file, refresh browser

Cons

  • Vanilla JS can get messy at scale
  • No component reuse or framework niceties
B

SPA Framework + REST API

React/Svelte/Vue frontend with a proper build step. REST endpoints on the Axum server for reading/writing effect state. Frontend polls or uses SSE for updates.

Pros

  • Cleaner component architecture
  • Better for complex UI interactions (drag-and-drop reorder)
  • Hot module reload during frontend dev

Cons

  • Adds npm/node toolchain dependency
  • Two build steps (Rust + JS)
  • More complex deployment
C

HTMX + Server-Rendered

Server renders HTML fragments, HTMX handles interactivity. Minimal JS — the server drives the UI. Slider changes send HTMX requests that update the pipeline and return updated HTML.

Pros

  • Almost zero client-side JS
  • Rust templates (Askama/Tera) keep everything in one language
  • Trendy, simple mental model

Cons

  • Slider interactions feel laggy (round-trip per change)
  • Drag-and-drop reorder is awkward with HTMX
  • Less suited for highly interactive creative tools

My Recommendation: Option A

For a creative tool where the primary interaction is dragging sliders and watching a live stream change, the single-HTML + WebSocket approach hits the sweet spot. No build tooling to fight, instant feedback via WebSocket, and the UI complexity is bounded — it's fundamentally a list of effects with sliders, not a complex app. You can always migrate to a framework later if it outgrows vanilla JS.
