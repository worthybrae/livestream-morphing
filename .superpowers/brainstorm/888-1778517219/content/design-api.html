Design — Section 3: REST API + Pipeline Engine

How the frontend controls the backend

REST API Endpoints
── Effect Library ──
GET   /api/effects          # list all registered effects (id, name, param defs)
── Pipeline (the active effect chain) ──
GET   /api/pipeline         # get current pipeline: ordered list of {slot_id, effect_id, params, enabled}
PUT   /api/pipeline         # replace entire pipeline (reorder, add, remove effects)
PATCH /api/pipeline/:slot_id   # update one slot's params or enabled state
── Presets ──
GET   /api/presets          # list saved presets
POST  /api/presets          # save current pipeline as a new preset
PUT   /api/presets/:id/apply    # load a preset into the active pipeline
DELETE /api/presets/:id        # delete a preset
── Existing (unchanged) ──
GET   /stream/playlist.m3u8    # HLS playlist
GET   /stream/segment_N.ts    # HLS segments
Pipeline Engine — How It Works
// The pipeline is a Vec of slots, each holding an effect instance
struct PipelineSlot {
  slot_id: String,       // unique ID (uuid) for this instance
  effect: Box<dyn Effect>,
  params: ParamValues,   // current param values
  enabled: bool,         // toggle on/off without removing
}

struct Pipeline {
  slots: Vec<PipelineSlot>,
}

impl Pipeline {
  fn process_frame(&mut self, frame: &mut RawFrame, frame_number: u32) {
    let ctx = FrameCtx { frame_number, ... };
    for slot in &mut self.slots {
      if slot.enabled {
        slot.effect.apply(frame, &slot.params, &ctx);
      }
    }
  }
}
// Thread safety: pipeline runs on the processing thread,
// API runs on Axum's async threads.
// Solution: Arc<Mutex<Pipeline>> — lock is held briefly
// (just to read/write params or swap the slot list).
// The actual frame processing locks, copies params, then unlocks.

Key Decisions

Why slot_id, not array index?

Stable IDs survive reordering. If you drag effect #2 to position #4, its slot_id stays the same — the frontend doesn't lose track of which slider belongs to which effect.

Why PUT for full pipeline?

Reordering and add/remove are structural changes to the whole list. A single PUT with the new ordered list is simpler and less error-prone than individual insert/delete/move operations.

Why PATCH for params?

Slider drags are frequent, small updates. PATCH on a single slot is lightweight — just the params that changed, no need to re-send the whole pipeline.

Presets as TOML files

Human-readable, version-controllable, shareable. A preset is just a pipeline snapshot: ordered effect IDs + their param values. Easy to hand-edit or commit to git.
